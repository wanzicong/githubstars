# 死代码管理

## 定义

死代码（Dead Code）是指以下任何形式的代码：

1. **未使用的代码**：函数、类、变量、导入等从未被引用或调用
2. **被注释掉的代码**：被注释掉的大段代码块（非文档性注释）
3. **不可达代码**：在任何执行路径下都无法到达的代码
4. **冗余代码**：功能已被其他代码完全替代但未删除的旧实现
5. **无效条件分支**：条件恒为 true/false 导致的分支不可达

## 强制性要求

在**任何**提交之前，确保：

* \[ ] 无未使用的函数、方法或类
* \[ ] 无未使用的变量、常量或导入语句
* \[ ] 无被注释掉的大段代码块（超过 3 行的连续注释代码）
* \[ ] 无不可达的代码路径
* \[ ] 无已被替代但未删除的旧实现
* \[ ] 无未使用的类型定义、接口声明

## 检测方法

### 自动检测工具

* **TypeScript/JavaScript**：使用 `ts-prune` 检测未使用的导出，使用 ESLint 的 `no-unused-vars` 规则
* **Java**：使用 IDE 内置的死代码检测（IntelliJ IDEA：Code > Inspect Code），或使用 SpotBugs/PMD
* **Python**：使用 `vulture` 检测死代码，使用 `ruff` 的 `F401` 规则检测未使用的导入

### 手动审查要点

1. 搜索被注释掉的代码块（正则：`^\s*//\s*(function|class|if|for|while|return|const|let|var|import|export|public|private|protected)`）
2. 检查是否存在仅被测试引用但测试本身已废弃的代码
3. 审查条件编译块中已不再使用的分支
4. 验证所有导出的符号在模块外部确实有引用者

## 处理策略

### 被注释掉的代码

* **立即删除**：被注释掉的代码块不得保留在代码库中。如需追溯，使用 `git log` 或 `git blame`
* **例外**：仅当注释掉的代码附带明确的 TODO/FIXME 标记，且说明了何时恢复、为什么暂时注释时，允许暂留。此类例外必须附带 issue 追踪编号

```
// ACCEPTABLE — 带有明确的恢复计划和追踪编号
// TODO(#1234): 当后端 API v2 上线后恢复此逻辑
// const result = await legacyApi.fetch()

// UNACCEPTABLE — 无解释的被注释代码
// function oldHandler(req, res) {
//   const data = req.body
//   ...
// }
```

### 未使用的代码

* **公共 API**：对外暴露的公共 API 即使当前未被内部使用，若属于计划中或已文档化的接口，允许保留（需添加 `@public` 注释说明）
* **内部代码**：所有内部未使用的代码必须删除
* **依赖包的导出**：如果某个导出仅用于外部消费者，添加注释标记 `// @public-api` 以防止误删

### 不可达代码

* 不可达代码是潜在 bug 的信号，必须修复使其可达或直接删除
* 检查是否因逻辑错误（如条件永远为 false、return 后的代码）导致不可达

## 定期清理流程

建议在每个迭代/冲刺结束时执行死代码清理：

1. 运行自动化死代码检测工具
2. 审查检测结果，区分真正的死代码和误报
3. 创建清理分支，逐文件删除死代码
4. 运行完整测试套件确保行为未改变
5. 提交清理结果（使用 `chore:` 类型的提交信息）

## 代码审查检查清单

在代码审查时，检查以下内容：

1. 是否有被注释掉的代码块需要清理？
2. 新增的导入是否都被使用？
3. 是否有函数/类被声明但从未调用？
4. 是否存在永远无法执行到的 `if` 分支或 `case` 分支？
5. 重构后旧实现是否已完全删除？
