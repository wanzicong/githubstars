# 性能优化

## 性能优先意识（P1）

性能问题不是"后面再优化"的次要事项——它是隐藏 Bug 的温床、用户体验的根基。任何需求/功能/Bug 修复都必须从性能角度前置审视。

**核心认知：**
- 🔴 性能问题会直接演变为功能 Bug：慢查询→请求超时→业务中断；内存泄漏→页面崩溃→数据丢失；渲染卡顿→点击无响应→用户误操作
- 🟠 好性能 = 好体验：响应速度是用户体验的第一指标，比视觉美观更直接影响留存率
- 🟡 性能优化必须**设计阶段介入**，而非上线后补救

### 五维审视清单

| 维度 | 必须回答的问题 |
|------|---------------|
| **数据层** | 是否存在 N+1 查询？索引是否覆盖查询条件？数据量增长 10 倍后 SQL 执行计划是否会退化？ |
| **网络层** | 单次请求返回数据量是否可控？是否需分页/懒加载？是否存在可合并的冗余请求？ |
| **渲染层** | 是否存在不必要的组件重渲染？大列表（>100 项）是否使用虚拟滚动？动画是否走 GPU 合成层？ |
| **内存层** | 定时器/事件监听/闭包引用是否在组件销毁时清理？大体积数据使用后是否及时释放？ |
| **并发层** | 高并发下是否存在锁竞争？数据库连接池/HTTP 连接池是否充足？事务边界是否最小化？ |

**执行要求：**
1. 需求分析阶段：评估新功能对现有系统各维度的性能冲击，识别潜在瓶颈点
2. 方案设计阶段：每个方案必须附带性能影响评估——预估响应时间、资源消耗、数据量敏感度
3. 编码实现阶段：遵循对应技术栈的性能最佳实践
4. Bug 修复场景：排查根因时同步检查是否存在性能退化信号（慢查询日志、内存异常增长、渲染帧率下降）
5. 禁止延期优化：不得以"先上线，性能后面再调"为由跳过性能审视——至少在设计和数据模型层面留好优化余地

## 模型选择策略

**Haiku 4.5** (具备 Sonnet 90% 的能力，节省 3 倍成本):

* 频繁调用的轻量级智能体
* 结对编程和代码生成
* 多智能体系统中的工作智能体

**Sonnet 4.6** (最佳编码模型):

* 主要的开发工作
* 编排多智能体工作流
* 复杂的编码任务

**Opus 4.6** (最深的推理能力):

* 复杂的架构决策
* 最高级别的推理需求
* 研究和分析任务

## 上下文窗口管理

避免使用上下文窗口的最后 20% 进行:

* 大规模重构
* 跨多个文件的功能实现
* 调试复杂的交互

上下文敏感性较低的任务:

* 单文件编辑
* 创建独立的实用工具
* 文档更新
* 简单的错误修复

## 扩展思考 + 计划模式

扩展思考默认启用，最多保留 31,999 个令牌用于内部推理。

通过以下方式控制扩展思考：

* **切换**：Option+T (macOS) / Alt+T (Windows/Linux)
* **配置**：在 `~/.claude/settings.json` 中设置 `alwaysThinkingEnabled`
* **预算上限**：`export MAX_THINKING_TOKENS=10000`（bash）或 `$env:MAX_THINKING_TOKENS = "10000"`（PowerShell）
* **详细模式**：Ctrl+O 查看思考输出

对于需要深度推理的复杂任务:

1. 确保扩展思考已启用（默认开启）
2. 启用 **计划模式** 以获得结构化方法
3. 使用多轮批判进行彻底分析
4. 使用分割角色子代理以获得多元视角

## 构建故障排除

如果构建失败:

1. 使用 **build-error-resolver** 智能体
2. 分析错误信息
3. 逐步修复
4. 每次修复后进行验证
