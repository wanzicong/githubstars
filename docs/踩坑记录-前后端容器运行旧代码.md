# 踩坑记录 — 前后端容器运行旧代码（改了代码不重建镜像不生效）

> **记录日期**：2026-08-01
> **影响范围**：生产容器（githubstars-backend / githubstars-frontend）、本地 Vite dev server
> **严重级别**：高（改了代码、本地 dist 验证通过，但用户实际访问的容器仍是旧代码，新功能/修复全部不生效）

---

## 问题现象

开发「仓库加入 Agent 对话上下文」功能后，用户在**容器环境**使用时遇到两类看似独立的报错：

1. 前端偶发 `Minified React error #185`（Maximum update depth exceeded，setState 无限循环）。
2. 对话时容器后端报 `EPIPE` / `TypeError: fetch failed`。

排查发现：**用户访问的容器（前端 10003 / 后端 10004）与本地 dev（10001）跑的全是旧代码**：

| 进程/容器 | 启动/构建时间 | 代码修改时间 | 结论 |
|-----------|--------------|-------------|------|
| 本地 vite dev (PID 51924) | 13:02 | 19:38 | 旧（HMR 对 zustand store 不可靠，partialize 未生效，localStorage 无 contextItems） |
| 前端容器镜像 | 17:33 | 19:38 | 旧（代码构建进镜像，未重建） |
| 后端容器镜像 | 17:33 | 19:38 | 旧（无 ensure 端点、无 EPIPE 重试强化） |
| 本地后端 dist (PID 35436) | 19:42 | 19:38 | **新**（唯一跑新代码的，但用户没访问它） |

---

## 根本原因

**前端代码是「构建时打包」进 nginx 镜像的，不是运行时挂载**：

1. `Dockerfile.frontend` 是多阶段构建，`turbo prune` → `npm ci` → `tsc -b + vite build` → 把 `dist/` 拷进 nginx 镜像（[Dockerfile.frontend](../Dockerfile.frontend)）。
2. **改了前端代码后，必须 `docker build` 重建镜像 + `docker compose up -d --force-recreate` 重建容器**，否则容器里永远是最初构建时的旧 `dist/`。
3. 后端同理：`Dockerfile.backend` 把编译产物打进镜像，改后端代码不重建镜像，容器内没有新路由（如 `/api/trending/ensure`）。

**本地 Vite dev 的 HMR 对 zustand store 不可靠**：store 结构变更（新增 `contextItems` 字段、改 `partialize`）后，运行中的 dev server 热替换不会重建 store，localStorage 读到的仍是旧结构。表现为「代码明明改了，页面行为却是旧的」。

**加剧因素**：本地同时存在多个孤儿 vite 进程（10001/10006），`preview_start` 的 `autoPort` 又不断分配新端口，导致「到底哪个进程在跑、跑的是不是新代码」难以判断。

---

## 正确做法

### 1. 容器环境改代码后必须重建镜像

```bash
# 后端改了 → 重建后端镜像 + 容器
docker build -t githubstars-backend -f Dockerfile.backend .
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --force-recreate backend

# 前端改了 → 重建前端镜像 + 容器
docker build -t githubstars-frontend -f Dockerfile.frontend .
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --force-recreate frontend
```

> ⚠️ 必须带 `--env-file .env.production`（见 [踩坑记录-DockerCompose环境变量加载失败](踩坑记录-DockerCompose环境变量加载失败.md)）。

### 2. 验证容器跑的是新代码，而不是「以为」是

重建后**必须 curl 一个「新代码才有的端点/行为」**来证明：

```bash
# 本次用 ensure 端点（旧镜像没有它，返回 404；新镜像返回 201）
curl -X POST http://localhost:10003/api/trending/ensure \
  -H "Content-Type: application/json" \
  -d '{"repos":[{"fullName":"octocat/Hello-World"}]}'
# 返回 {"success":true,"repos":[{"fullName":"octocat/Hello-World","id":...}]} → 新代码生效
```

### 3. zustand store 结构变更后，重启 dev server 而非依赖 HMR

改了 `agentChat.ts` 等 store 的字段/partialize 后，**停掉 vite 重启**，并清一次 localStorage（或确认 partialize 生效），不要信热替换。

### 4. 排查前先对齐「进程时间 vs 代码时间」

遇到「改了没生效」类问题，第一步先对比：

```bash
stat -c '%y' <修改的源文件>                          # 代码修改时间
wmic process where "processid=<pid>" get creationdate  # 本地进程启动时间
docker inspect <容器> --format '{{.State.StartedAt}}'  # 容器启动时间
docker image inspect <镜像> --format '{{.Created}}'    # 镜像构建时间
```

**进程/镜像时间早于代码时间 = 跑的是旧代码**，这是最该先排除的根因。

---

## 验证检查清单

- [ ] 重建镜像后 `docker compose ... up -d --force-recreate`，容器状态 `healthy`。
- [ ] curl 新端点返回预期（不是 404），证明容器是新代码。
- [ ] 浏览器实测目标页面：功能正常、无 `React error #185`、无白屏。
- [ ] localStorage 中 store 的 partialize 字段与新代码一致（如含 `contextItems`）。
- [ ] 多余的孤儿 vite / node 进程已清理，避免端口与「跑哪份代码」的混淆。

---

## 教训

1. **「编译通过 / dist 验证 OK」≠「用户环境生效」**。容器是构建时快照，不改镜像就永远是旧代码。改完代码的「最后一公里」是**重建镜像 + 重建容器 + curl 新端点证明**。
2. **HMR 不是万能的**：对 zustand store、路由表、全局单例这类「启动时初始化一次」的结构，热替换常常不生效，表现为「代码改了行为没变」，此时应重启 dev server。
3. **环境问题优先用「时间对齐」排除**：进程/镜像构建时间早于代码修改时间，就是旧代码，不用纠结业务逻辑。
4. **多个孤儿 dev 进程是排查噪音**：及时清理，否则会在「到底访问的是哪份代码」上浪费大量时间。
