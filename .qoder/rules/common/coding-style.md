# 编码风格

## 基础错误零容忍（P0）

以下三类错误在任何情况下均不可接受，提交前必须逐项检查：

1. **语法错误** — 代码无法通过编译器/解释器解析
2. **编译错误** — 编译型语言必须编译通过
3. **中文乱码** — 所有中文字符串、注释、日志输出编码正确

## 变更验证闭环

任何代码变更必须经历以下完整循环：

```
代码审查 → 编译通过 → 重启服务 → 测试验证 → 发现问题 → 修复 → 重新验证
```

该循环必须执行至**所有测试通过且无新问题引入**为止。

## 不可变性（关键）

始终创建新对象，绝不改变现有对象：

```
// 伪代码
WRONG:  modify(original, field, value) → 原地修改 original
CORRECT: update(original, field, value) → 返回包含更改的新副本
```

理由：不可变数据可以防止隐藏的副作用，使调试更容易，并支持安全的并发。

## 存量和现有逻辑感知（P1）

任何修改不是孤岛——必须先感知"已经存在什么"，再决定"应该改什么"。

**三步感知法：**

| 步骤 | 动作 | 方法 |
|------|------|------|
| **反向感知** | 向上追溯：谁在调用我打算修改的方法/组件/接口？列出所有调用方及使用场景 | Grep 搜索引用、IDE "查找引用"、调用链反向追踪 |
| **正向感知** | 向下追踪：修改的逻辑会触发哪些下游行为？数据最终写入哪里？哪些缓存会失效？ | 调用链正向追踪、数据库外键关联、缓存 Key 匹配 |
| **横向感知** | 同级扫描：是否存在与本次变更相似但不完全相同的逻辑？（类似 API 端点、平行组件、同表其他操作） | 同目录/同包文件扫描、同表名的其他方法、路由文件中相邻路由 |

**影响清单（变更前必须输出）：**

```
变更: [简述本次要做什么]

反向影响（谁调用了被修改的代码）：
  - FooService.getBar() [FooService.java:88] — 被 OrderController、AdminController 调用
  → 影响评估: 需确认调用方是否兼容新签名/新行为

正向影响（修改后会触发什么下游变化）：
  - 数据写入 user_log 表 [UserLogMapper.java:15]
  - 缓存键 user:info:{id} 被清除 [CacheService.java:33]
  → 影响评估: 需确认日志格式/缓存策略是否同步调整

横向关联（同类型逻辑是否需要同步修改）：
  - /api/v1/users 接口也存在类似权限校验逻辑 [AuthFilter.java:55]
  → 影响评估: 需确认是否一并更新，避免行为不一致
```

## 多角色全局思考（P1）

当遇到需求或 Bug 时，禁止仅从单一技术点出发思考。必须同时站在以下四个角色视角审视：

| 角色 | 关注维度 |
|------|----------|
| **产品架构师** | 对整体产品的影响范围、是否与其他功能模块存在关联或冲突、在系统全局中的定位是否合理 |
| **UI 交互师** | 用户交互流程是否自然、视觉反馈是否到位、状态转换是否有平滑过渡、边界态（Loading/Empty/Error）体验是否完整 |
| **前端架构师** | 组件拆分是否合理、数据流是否清晰、状态管理方案是否恰当、性能影响、可复用性与可维护性 |
| **后端架构师** | API 设计是否 RESTful、数据模型变更是否向后兼容、数据库查询性能、并发与事务处理是否安全、是否需要新增接口 |

**执行要求：**
1. 需求分析阶段：从四个角色各自提出至少 1 个关注点，汇总后再进入代码库探索
2. 方案设计阶段：每个方案必须包含四个角色的影响评估
3. Bug 修复场景：除定位根因外，必须评估该 Bug 是否在其他模块存在同类问题、修复是否会引入副作用

## 文件组织

多个小文件 > 少数大文件：

* 高内聚，低耦合
* 通常 200-400 行，最多 800 行
* 从大型模块中提取实用工具
* 按功能/领域组织，而不是按类型组织

## 错误处理

始终全面处理错误：

* 在每个层级明确处理错误
* 在面向用户的代码中提供用户友好的错误消息
* 在服务器端记录详细的错误上下文
* 绝不默默地忽略错误

## 输入验证

始终在系统边界处进行验证：

* 在处理前验证所有用户输入
* 在可用时使用基于模式的验证
* 快速失败并提供清晰的错误消息
* 绝不信任外部数据（API 响应、用户输入、文件内容）

## 代码质量检查清单

在标记工作完成之前：

* \[ ] 代码可读且命名良好
* \[ ] 函数短小（<50 行）
* \[ ] 文件专注（<800 行）
* \[ ] 没有深度嵌套（>4 层）
* \[ ] 正确的错误处理
* \[ ] 没有硬编码的值（使用常量或配置）
* \[ ] 没有突变（使用不可变模式）
